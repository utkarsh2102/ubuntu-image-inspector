# Data contract

Everything under `site/data/` is generated by `collector/` and committed. All
files are emitted with sorted keys and compact separators, and only
`index.json` carries a timestamp — so an unchanged collection produces
byte-identical output and `git status` stays meaningful.

`schemaVersion` is present on every document. Breaking changes bump it.

## Identity

| Entity | Form | Example |
|---|---|---|
| Series | codename | `questing` |
| Milestone | `<codename>:<slug>` | `questing:snapshot-3`, `questing:ga`, `questing:ga.1` |
| Image | `<publishType>/<arch>` | `live-server/arm64+largemem` |
| Package | `(name, version)` | arch qualifier stripped; raw form kept in detail |
| Snap | `(name, revision)` | revision is the identity, channel is not |

Milestone ordering is `(phase, n, point)` with phase ranked
`snapshot < alpha < beta < rc < ga < point`. The resulting dense `order`
integer is emitted so the client never re-derives it.

## `index.json` — eager, ~8 KB

```jsonc
{
  "schemaVersion": 1,
  "generatedAt": "2026-09-21T02:10:00Z",
  "collector": { "version": "0.1.0" },
  "metrics": [ { "id": "bytes", "label": "Image size", "unit": "bytes" } ],
  "series": [
    {
      "codename": "questing", "version": "25.10", "lts": false,
      "status": "eol",                       // dev | supported | eol
      "created": "2025-04-17", "released": "2025-10-09", "eol": "2026-07-09",
      "milestones": [
        {
          "id": "questing:snapshot-3", "kind": "snapshot", "n": 3, "point": 0,
          "order": 2, "label": "Snapshot 3", "date": "2025-07-28T02:32:13Z",
          "host": "old-releases", "baseUrl": "https://old-releases.ubuntu.com/..."
        }
      ]
    }
  ],
  "images": [
    { "id": "live-server/amd64", "publishType": "live-server", "arch": "amd64",
      "label": "Server (amd64)", "hasManifest": true }
  ],
  "availability": { "questing": { "live-server/amd64": [0, 1, 2, 3, 4, 5] } }
}
```

`availability` maps series → image → the milestone `order` values where that
image exists, so selectors can be populated before any metrics load.

## `metrics/<codename>.json` — lazy, ~8 KB

Row-as-array with a `fields` header (about 45 % smaller than objects).
**This file alone powers the trend chart**; manifests are never needed to draw it.

```jsonc
{
  "schemaVersion": 1,
  "series": "questing",
  "fields": ["m","i","bytes","built","pkgs","snaps","snapBytes","installedKB","flags"],
  "points": [
    ["questing:snapshot-3","live-server/amd64",2134083584,
     "2025-07-28T13:46:38Z",696,3,1491378176,2338451,[]]
  ]
}
```

| Field | Meaning |
|---|---|
| `bytes` | image size, **compressed**, from `Content-Length` |
| `snapBytes` | sum of seeded snap download sizes, **compressed** |
| `installedKB` | sum of `Installed-Size`, **uncompressed KB** |
| `flags` | `size-only`, `manifest-missing`, `pkg-meta-incomplete`, `snap-size-incomplete` |

## `detail/<codename>/<slug>/<publishType>-<arch>.json` — on demand, ~20 KB

```jsonc
{
  "schemaVersion": 1,
  "milestone": "questing:snapshot-3",
  "image": "live-server/amd64",
  "bytes": 2134083584,
  "built": "2025-07-28T13:46:38Z",
  "sha256": "…",
  "url": "https://old-releases.ubuntu.com/…iso",
  "manifestUrl": "https://old-releases.ubuntu.com/…manifest",
  "packages": [ ["adduser", "3.152ubuntu1"] ],
  "snaps": [
    { "name": "core24", "channel": "stable", "rev": 1055,
      "bytes": 70029312, "version": "20250714", "type": "base" }
  ],
  "totals": { "pkgCount": 696, "snapCount": 3,
              "snapBytes": 1491378176, "installedKB": 2338451 },
  "coverage": { "pkgMetaKnown": 696, "pkgMetaTotal": 696,
                "snapSizeKnown": 3, "snapTotal": 3 },
  "flags": []
}
```

`coverage` is what lets the UI say *how complete* a total is instead of
implying it is the whole story. A snap whose size could not be resolved has
`bytes: null` — never `0`.

## `pkgmeta/<codename>-<arch>.json` — on demand, ~150 KB gzipped

Keyed `name → version → entry`, restricted to packages some image of that
series actually contains.

```jsonc
{
  "schemaVersion": 1, "series": "questing", "arch": "amd64",
  "pkgs": {
    "bash": {
      "5.2.37-1.1ubuntu1": {
        "i": 2188,                  // Installed-Size, UNCOMPRESSED KB
        "d": 919876,                // .deb size, bytes
        "src": "bash",              // source package
        "sec": "shells", "pri": "required", "ess": true,
        "dep": ["base-files","debianutils","libc6","libtinfo6"],
        "rec": ["bash-completion"],
        "task": ["minimal"]
      }
    }
  },
  "sources": { "questing:snapshot-3:main": "20250728T134638Z" }
}
```

`sources` records which archive timestamp each component was read at, so a
figure can be traced back to the index it came from.

### Units — the rule the whole dashboard depends on

`i` is **uncompressed kilobytes**. `bytes` and `snapBytes` are **compressed
bytes**. Images are squashfs-compressed; the compression ratio is not measured
anywhere in this project, so installed size cannot be converted into image
size. The UI presents them as separate measured quantities and never sums them,
and the LLM system prompt repeats this as a hard rule.

## `_state/` — diagnostics

| File | Purpose |
|---|---|
| `collected.json` | Ledger of milestones already collected; lets a re-run skip immutable ones |
| `unparsed.json` | Published artifacts whose filenames did not parse. CI fails if the count rises — filename drift becomes a reviewable diff instead of silent data loss |
| `errors.json` | Fetch failures, with URL and reason |

## Adding a metric

1. Append to `METRICS` in `collector/uii/config.py`.
2. Emit the field in `_metrics_doc` in `collector/uii/collect.py`.
3. Bump `schemaVersion` only if an existing field's meaning changes.

The chart's metric selector is generated from `index.metrics`, so nothing in
the frontend needs editing.
